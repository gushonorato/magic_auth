# AGENTS.md

This file provides guidance to AI coding agents (such as Claude Code) when working with code in this repository.

Magic Auth is a passwordless (email one-time password) authentication library for Phoenix, published on Hex. It is
a library, not an app: it runs inside a host Phoenix project, configured through `config :magic_auth` and a callbacks
module generated by `mix magic_auth.install`.

## Commands

```bash
mix deps.get
mix magic_auth.setup_test_db     # drops and recreates magic_auth_test (Postgres on localhost, postgres/postgres)
mix test                          # full suite, including the slow E2E installer tests
mix test --exclude e2e            # skip E2E tests
mix test test/magic_auth_test.exs:42
mix format                        # line_length is 120
mix docs
```

- `mix magic_auth.setup_test_db` builds the test schema from the installer's migration template
  (`priv/templates/magic_auth.install/*_create_magic_auth_tables.exs.eex`) plus a `users` table. Re-run it after
  changing that template.
- E2E tests (`test/e2e`, tagged `:e2e`) run `mix phx.new` with the globally installed `phx_new` archive inside `tmp/`,
  then run `mix magic_auth.install` on the generated project and assert on the files. Their result depends on the
  archive version: CI pins `phx_new 1.7.18` (Elixir 1.18.2 / OTP 27.2), while a newer archive generates different
  code (e.g. Phoenix 1.8's `hooks: {...colocatedHooks}` in `app.js`).

## Architecture

- **Host configuration is resolved at runtime.** `MagicAuth.Config` reads `Application` env for the host's repo,
  router, endpoint and callbacks module. Library code never references host modules directly.
- **All database access goes through `MagicAuth.Repo` and `MagicAuth.Multi`.** These wrap the host repo and pass
  `repo_opts` (default `[magic_auth: true]`, or a function returning e.g. `[prefix: tenant]`) on every call, which is
  what makes multi-tenancy work. Don't call the host repo directly.
- **Callbacks (`MagicAuth.Callbacks`) are the extension point.** The host implements `log_in_form/1` and
  `verify_form/1` (UI), `one_time_password_requested/1` (sending the email), `log_in_requested/1` (`:allow`, `:deny`
  or `{:allow, user_id}`; the user is then loaded through the `get_user` config into `:current_user`) and
  `translate_error/2`. The installer generates the host implementation from
  `priv/templates/magic_auth.install/magic_auth.ex.eex`.
- **Log in flow:** `MagicAuth.LoginLive` creates the one-time password (`MagicAuth.create_one_time_password/1`) →
  `MagicAuth.PasswordLive` collects the code and redirects to `MagicAuth.SessionController.verify/2` →
  `MagicAuth.log_in/3` checks the rate limit, verifies the bcrypt-hashed code, calls `log_in_requested/1` and creates
  a `MagicAuth.Session` (token in the Plug session, optional remember-me cookie).
- **Routing:** `use MagicAuth.Router` plus the `magic_auth/2` macro define the routes and a generated
  `__magic_auth__/2` function on the host router, which the library uses to build every path
  (`MagicAuth.Config.router().__magic_auth__(:password, %{email: email})`). `MagicAuth` also exposes the plugs
  (`fetch_magic_auth_session`, `require_authenticated`, `redirect_if_authenticated`) and `on_mount` hooks.
- **Rate limiting:** `MagicAuth.RateLimit` (Hammer, ETS backend) limits one-time password requests and log in attempts
  per downcased email. It runs in the host's supervision tree through `MagicAuth.children()`, and
  `enable_rate_limit: false` disables it.
- **JavaScript:** `priv/static/index.js` exports `MagicAuthHooks`. `package.json` points `main` there so the host's
  bundler resolves `import {MagicAuthHooks} from "magic_auth"` from `deps/`.
- **Installer (`Mix.Tasks.MagicAuth.Install`):** injects code into the host's `config.exs`, router, `application.ex`
  and `app.js` with string matching. It must be idempotent (skip if already injected) and fall back to printing
  manual instructions when the expected pattern isn't found. It supports umbrella projects.

## Tests

- Tests use a fake host app in `test/support` (`MagicAuthTestWeb.Router`, `MagicAuthTestWeb.Endpoint`,
  `MagicAuthTest.Repo`). Callbacks are the Mox mock `MagicAuthTestWeb.CallbacksMock`, set up in
  `test/test_helper.exs`.
- Tests that change `:magic_auth` app env use `preserve_app_env` or `config_sandbox` from `MagicAuthTest.Helpers`.
  Tests that write files use `use_tmp_dir`, which `cd`s into a fresh directory under `tmp/`.

## Changelog

- `CHANGELOG.md` follows Keep a Changelog. New entries go under `## [Unreleased]`.
- Don't add `CHANGELOG.md` entries for updates to the version in installation snippets (e.g. `{:magic_auth, "~> 0.2.1"}`
  in `guides/getting_started.md`). Bumping them is part of the release routine, not a change users need to know about.

## Releasing

1. Bump `@version` in `mix.exs`, `"version"` in `package.json` and the installation snippet in
   `guides/getting_started.md`.
2. Rename `## [Unreleased]` in `CHANGELOG.md` to `## [x.y.z] - YYYY-MM-DD`.
3. Commit as `release x.y.z`, tag `vx.y.z`, and push the branch and the tag.
4. `mix hex.publish` prompts for the local Hex key password, so the maintainer must run it in their own terminal.
